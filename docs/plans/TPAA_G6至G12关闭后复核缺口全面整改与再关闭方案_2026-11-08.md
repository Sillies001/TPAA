## 1. 目标与裁决原则

本波次的目标不是修饰已有关闭报告，而是使软件在以下四个方面同时成立：

1. 源代码遵守 TPAA V8.0 总体设计、ED-2.0 工程设计及 v33 三份 Patch；
2. GUI 的信息架构、页面结构、控件、布局、三主题和受控交互与 `TPAA_训练复盘交互Demo_v33.html` 一致；
3. 所有显示数据均由真实 Application/Canonical/Storage 链路产生，无 Demo 数值、随机曲线、latest 回退、跨批次借数或静默降级；
4. 阶段状态、W9 结论和证据只反映实际通过的门禁，不以脚本中的硬编码 `PASS` 代替执行结果。

裁决规则：

- 当前将 G6～G11 统一视为 `IN_PROGRESS_REMEDIATION`，G12 维持 `IN_PROGRESS_EXTERNAL_DOORS_OPEN`；
- W9 必须维持 `NO_GO`，`product_complete=false`，`release_ready=false`；
- 任一阶段只有在功能、权限、数据真实性、GUI 忠实度、自动测试和人工门均通过后，才可重新写为 `CLOSED_LOCAL_WITH_GATES`；
- G12 只有在 G6～G11 全部重新关闭且安装包、Linux/Service、SBOM/许可证/漏洞、目标 workload、真实角色视觉验收全部完成后，才可评估 `PRODUCT_COMPLETE`；
- `PRODUCT_COMPLETE` 仍不等于 `RELEASE_READY`，后者必须由独立 W9 发布裁决产生。

## 2. 复核确认的缺口

### 2.1 状态与证据真实性

- `baseline/CB-1.17.0/canonical/W9_REAGGREGATION.json` 在外部门仍开放时错误声明 `product_complete=true`；
- G10 关闭器把 `NOT_ADMITTED` 视为关闭条件，和“26 视图完整功能”目标冲突；
- G6～G11 关闭器存在预写 `PASS`、未实际执行所声明门禁的问题；
- G10/G11 关闭记录的 `next_phase` 不正确；
- 主实施方案仍记录 `G6～G12=NOT_STARTED`，和工作树事实不一致；
- GUI 符合性矩阵仍停留在 `TARGET_FROZEN_IMPLEMENTATION_PENDING`，没有表达逐视图真实状态。

### 2.2 GUI 与 Demo v33 忠实度

- 视觉矩阵虽生成 156 张图片，但存在跨视图重复：V24 图片实际为 V26，V09 与 V10 重复；
- `g12_visual_matrix.py` 的视图映射与 `V33_FINAL_VIEW_REGISTRY.json` 不一致，并且没有验证导航后的真实视图 ID；
- 布局检查只检查少量顶层元素，不能识别子控件裁切、文字重叠、溢出和错误页面；
- V24 受控入口必须从 V08 进入，不能用直接路由冒充验收；
- V26 筛选栏被绝对定位规则影响，真实截图中不可见；
- V03、V11、V18、V22 等页面仍为占位/未准入状态，与 Demo 的完整页面结构和评估功能不一致；
- V24 的实际页面存在徽标/文本重叠，且分析维度、几何表达和左右视角信息不完整。

### 2.3 后端与运行时功能

- G6 历史总览尚缺任务/装备指标的正式准入、可比性和 V01 完整读模型；
- G7 V26 尚缺完整筛选、非发射事件语义和工作台闭环；
- G8 V24/双视角尚缺完整多维分析、事件窗口与几何呈现；
- G9 只有回放上下文骨架，API 丢失 `release_id/context_id/perspective` 精确上下文，媒体/游标/2D/3D 回放尚未实现；
- G10 的 P3 Model Profile、报告修订、治理变更、基本飞行、来源覆盖等能力仍未准入；
- 历史 Canonical JSON 解析失败时会静默返回空对象，可能把损坏数据误报为 EMPTY；
- G5～G11 激活器逐级硬编码可接受基线列表，可维护性差，应该由受信任基线谱系和能力权威统一解析；
- G9 生成目录名错误使用 `g9-cb-1.13.0`，与实际 CB-1.14.0 不一致。

### 2.4 工程与设计同步

- G6～G12 没有对 R3.3 总体/工程设计主体形成可验证的受控同步；
- G11 还缺安装包 smoke、Linux/Service profile、SBOM/license/vulnerability 和目标 workload 性能证据；
- 现有 G12 “设计封版”只声明同步，没有校验设计输入、机器权威和实现之间的哈希/覆盖关系。

## 3. 分阶段整改工作包

### R0：真值回退与证据止血

修改：

- 将 W9、G12 统一改为 `NO_GO / product_complete=false / release_ready=false`；
- 主实施方案登记 G6～G11 为 `IN_PROGRESS_REMEDIATION`、G12 为 `IN_PROGRESS_EXTERNAL_DOORS_OPEN`；
- 符合性矩阵增加逐视图实现状态、门禁状态和开放缺口，不再以单一全局字符串冒充完成度；
- G6～G12 旧“关闭”报告加复核撤销声明，保留历史文件但不得作为当前关闭依据；
- 建立本方案和一份机器可读整改状态文件。

退出门：所有状态来源一致；任何脚本不得输出 `PRODUCT_COMPLETE` 或 G6～G12 已关闭。

### R1：受信任谱系、关闭执行器与证据模式

修改：

- 建立统一的受信任谱系/能力解析器：只接受已锁定父链、有效 lock、显式 approval 与实际组件能力；
- 移除 G5～G11 激活器中的逐代基线名称元组；
- 建立共享关闭门禁执行器，记录命令、退出码、耗时、摘要和产物哈希；
- 关闭器仅消费实际执行证据，缺项或失败时生成 `IN_PROGRESS`，不得硬编码 PASS；
- 修正 G9 生成目录为 `generated/g9-cb-1.14.0/`；
- 为谱系篡改、能力缺失、关闭器漏跑门禁和证据重放增加负面测试。

退出门：Ruff/Mypy、successor/codegen `--check`、谱系与关闭器负测全部通过。

### R2：G6 历史聚合与 V01

修改：

- 为任务/装备指标增加独立准入状态、定义版本、单位、方向、适用范围和可比性原因；
- 历史总览只聚合同 scope/metric-definition/quality 可比数据；
- Canonical JSON 损坏必须返回 DEGRADED/ERROR 并记录审计，禁止静默转 EMPTY；
- V01 实现 Demo 对应的批次卡、趋势、任务/装备分层、筛选、钻取及明确四态；
- 添加跨批次、跨定义、损坏 JSON、空批次、分页和权限测试。

退出门：G6 Application/API/GUI/视觉门全部通过后才可重新关闭 G6。

### R3：G7 单批次事件工作台与 V26

修改：

- 修复 V26 筛选栏布局，确保三主题、100%/150% DPI 和 Ribbon 两态均可见；
- 完成批次/架次/主体/事件类型/质量/时间筛选与游标分页；
- 区分武器发射、非发射、未知和数据不足，不允许把非发射伪装为发射事件；
- 完成事件列表、详情、空态、降级态、错误态、权限态；
- 页面 URL/状态与精确批次绑定，禁止 latest 回退。

退出门：直接 API 负测、V26 功能测试和真实 WebEngine 截图均通过。

### R4：G8 双视角、V24 与事件窗口

修改：

- V04/V05/V06/V08/V20/V21 完成攻防双视角字段、权限和数据绑定；
- V24 仅允许从 V08 受控入口进入，grant 必须绑定 release/context/WE/perspective 且一次性或短时有效；
- 实现 terminal/adjudication/window 三维独立状态、半开区间、几何标记、Cluster 关系和 supersession 展示；
- Strike target 视角和跨批次访问继续失败关闭；
- 按 Demo 修复页面网格、卡片密度、标尺、图例、徽标和文字重叠。

退出门：V08→V24 正向路径及直接访问/伪造 grant/跨批次/越权负测通过，6 个专项页视觉核对通过。

### R5：G9 精确回放与 V03

修改：

- API/DTO/前端请求必须携带并验证 `release_id/context_id/weapon_event_id/perspective`；
- 回放深链和返回栈保留完整上下文，拒绝不匹配参数；
- 接入真实媒体清单、游标、轨迹、2D/3D 可用性和证据索引；无媒体时诚实 EMPTY/N_A；
- 实现时间轴、播放控制、速度、视角、事件锚点和证据联动；
- 禁止随机轨迹、静态 Demo 数值和跨批次媒体借用。

退出门：上下文篡改负测、回放状态机测试、V03 三主题/键盘/焦点/高 DPI 验收通过。

### R6：G10 其余视图与评估功能

### R7：视觉矩阵与 Demo 忠实度工具
