**新基线目标：** TPAA V8.0 / ED-2.0 / CB-1.1.0 / Rebaseline R3  
**来源：** R39 交付包（总体方案 V7.2 + ED-1.5.12）  
**日期：** 2026-09-19

## 1. 提炼结论

R39 已经不是“方案尚未成形”的状态，而是一个经过多轮独立审查后形成的大型知识库。其主要剩余风险来自**同一事实在多个文档中重复定义**，而不是 116 项指标本体尚未稳定。新基线因此采用“保留知识、重建定义权”的策略。

冻结继承的可验证事实：

- P1 指标：**116** 项；R39 旧交付标签 1C=32、1D=84，R3.2 已迁移为 M2 foundation batch=32、M3 remainder batch=84。
- Subject：AIRCRAFT=40，MISSION_SYSTEM_INSTANCE=72，TARGET_PAIR=4。
- Value Kind：NUMERIC=107，STRUCTURED=9。
- R39 旧 1E 标签下可进入 P1 长期数值趋势：**104** 项；R3.2 由 M4 / WS-LONGITUDINAL 承接，其中 Aircraft=33，Mission-System=71。
- Input Authority：**661** 个 `(metric_code,input_field)` 精确绑定。
- 数据库目标 schema：**1.6.0**；不因文档重构虚构数据库迁移。

## 2. R39 中必须保留的成熟知识

### 2.1 数据与时间

Session Time 是计算权威；Clock reset 必须先于排序；Source Clock Segment 与 Time Alignment Domain 分层；gap、clock、authority、configuration、measurement-semantics 变化形成计算/series 边界。所有统计窗口使用半开区间 `[start,end)`。

### 2.2 Context 与历史重放

Session 不持有可变“当前 Context”指针。Context 是可修订但历史不可变的对象；Published Release 绑定实际使用的 Context IDs；历史读取不得重新运行 Resolver，也不得回退到 current/latest Scenario/Profile/Rule/Reference artifact。

### 2.3 Stable Subject

Aircraft 与 Mission-System Instance 是 P1 两条一级主体链。Mission-System 的 stable ID 必须从 master/canonical 一直贯穿 MetricContext、Published Metric、Observation、API、GUI 与 Longitudinal。TARGET_PAIR 只承担参考/评估质量证据，不建立长期主体。

### 2.4 Typed Metric Result

`value_kind` 决定唯一合法值槽。STRUCTURED 结果是对象而不是字符串，绑定固定 JSON Schema；长期趋势当前只接收符合条件的 NUMERIC。

### 2.5 Observation / Longitudinal

Aircraft Capability Observation 与 Mission-System Performance Observation 分 lane；二者均能从 Observation 回钻到 Published Metric、Evidence、Context、World 与 Release。Longitudinal 使用 `subject_type + subject_id + configuration_key + metric semantic/version + comparison key` 控制可比性。

### 2.6 Release / Provenance

Computed 只是 staging；Published 必须绑定 immutable Release。Release 绑定 compute job、input manifest、catalog、Context、World/Evidence 和 hash。历史 replay 不得用当前 Catalog 重新解释旧结果。

## 3. R39 反复发现新问题的根因分类

| 根因 | R39 中的典型表现 | 新基线处理 |
|---|---|---|
| 重复定义权 | `evaluation_context`、`metric_instance`、Session/Episode 在多处出现 current-looking 版本 | 字段级只允许机器契约一个权威 |
| 上位方案过度下沉 | 总体方案直接列 DB/DTO 字段，随后与工程方案 nullability 漂移 | 总体方案只定义业务语义与系统约束 |
| DTO 与 UI 投影混淆 | 同名对象既像 REST DTO 又像页面 ViewModel | API DTO 与 UI projection 明确分层 |
| 历史与当前混淆 | historical read 仍可能按 latest definition/context/artifact 解释 | exact ID/version/hash，fail-closed |
| Stable Subject 不贯通 | Mission-System 在某层有 ID、另一层从临时 track 猜 | stable subject 从 master 到 UI 全链路 |
| Typed value 收口不足 | numeric/text 旧模型与 structured 新模型并存 | value_kind 驱动单一值槽 |
| 长期趋势语义不闭合 | generic configuration alias、structured 隐式取子字段 | subject-specific key + numeric-only |
| 文档结构治理不足 | 历史段落仍像当前定义 | 新包不携带旧正文；历史只在本报告与迁移说明出现 |

## 4. 反复审查中形成的“失败知识”

以下不是需要删除的负担，而是新基线必须吸收的工程约束：

1. Context 多 revision 不能只靠 version string；历史主键必须是 `context_id`。
2. immutable Context configuration artifact 必须有 object/hash 绑定，只有版本字符串不够。
3. MetricDetail 的历史解释必须来自 immutable Metric Definition/Release，而非 current Catalog。
4. Mission-System lifecycle/identity 与 Observation/Trend 必须分清，configuration hash 变化不能偷换主体。
5. Aircraft Observation 不能依赖 P2～P4 才存在的 Human-Machine/factor 对象。
6. Stage 必须是正式可追踪对象，不能只作为 UI 标签或某个 Metric plugin 的临时窗口。
7. 当前/历史/引用投影必须在结构上分离，不能只靠“读者理解”。

## 5. 新基线继承与舍弃

**直接继承且继续作为机器权威：** `PHASE1_METRIC_CATALOG.json`、`METRIC_INPUT_AUTHORITY_MATRIX.json` 的精确内容。

**抽取后重新确立权威：** logical schema、critical DTO、Stage Registry、Phase Lifecycle、Core Rules。

**不再继承为 current 正文：** R39 各总体/工程文档中的重复字段表、重复 DTO 片段、legacy current-looking schema、历史审查补丁段。其价值仅作为追溯资料。

## 6. 重构原则

> 新版本不追求“把旧文档再写得更完整”，而追求“让同一事实只有一个地方能被修改”。

因此，新总体方案、新工程公共基线和各专业分册都由 `CB-1.0.0` 派生；字段、指标、Stage code、DTO、nullability 等不允许人工二次定义。
