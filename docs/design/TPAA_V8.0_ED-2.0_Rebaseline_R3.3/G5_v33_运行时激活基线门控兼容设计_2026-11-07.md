## 2. 设计原则：G5 是叠加层，不是替换

`CB-1.10.0` 是 `CB-1.9.0` 的**直接不可变后继且为其超集**：包含全部 96 条 G4 路由（`api.route.001-096`）+ 3 条 G5 读模型（`api.route.097-099`）。因此：

1. **G4 能力在 CB-1.10.0 下必须继续激活**：`batch_import`、G4 导入/修订、G2/G3 网关等不得因 CB 名变化而失效。
2. **门控语义从"等于某基线"改为"所属后继族"**：判断"该运行时具备哪些能力"应基于**能力准入状态机**（G2/G3/G4/G5 各自 ACTIVE），而非把 authority_root 名与单个 CB 字符串相等。
3. **存储基线校验接受后继**：DB schema 维持 1.10.0；`core_baseline` 校验接受 `CB-1.10.0`（其后继）而仍拒绝无关基线；CB-1.9.0 字节不变。

## 3. 受控设计（待 Codex 复核）

### 3.1 能力门控模型（核心改动）

引入**能力准入表**（由 active 权威驱动），替代 `g4_active = (parent.name == "CB-1.9.0")`：

```
capabilities = {G2, G3, G4, G5}  # 由 CB-1.10.0 各 approval 的 activation_status 得出
batch_import_active = G4 ∈ capabilities            # 不再依赖 CB 目录名字符串
weapon_event_active = G5 ∈ capabilities
```

- `production.py`：新增 `g5_active`（CB-1.10.0 approval ACTIVE）；`batch_import` 的激活条件改为 G4 能力激活（在 CB-1.9.0 与 CB-1.10.0 下均为 True）。
- 后向不变量：CB-1.9.0 下行为与现状完全一致（`g4_active=True`）；CB-1.10.0 下 G4、G5 同时激活。

### 3.2 存储基线兼容

- `tpaa_storage/bootstrap.py`：`G4_CORE_BASELINE` 改为"当前受控后继 = CB-1.10.0，父基线 = CB-1.9.0"的可配置/双值校验：
  - `expected_core_baseline` 接受 `CB-1.10.0`；`parent_core_baseline` 记录 `CB-1.9.0` 供 provenance/lineage。
  - DB schema 目标仍为 1.10.0；inventory 校验的期望清单在 CB-1.9.0/CB-1.10.0 下一致（无表增删）。
- 后向不变量：既有 CB-1.9.0 数据根、G4 验收闭环、`adopt_g4_successor --check` 全部不受影响（CB-1.9.0 目录与 lock 字节不变）。

### 3.3 安全与网关翻转

- `tpaa_security/api.py`、`gui_authority.py`：`generated_g4_authority` → `generated_g5_authority`（99 路由；G4 96 条在前，路由 ID/权限/审计不变）。

- `tpaa_api/gui_weapon_event.py`：3 条读模型路由（detail/window/perspective，经 `weapon_event_application.py`；DTO/权限/审计/来源语义；未知 WE fail-closed 404）。`unified.py`/`desktop.py` 注册。

### 3.4 前端翻转

- `frontend/gui-v33/src/main.ts`：bootstrap 校验 `CB-1.9.0`→`CB-1.10.0`、`catalog_version`→`CB-1.10.0:1.0.0`；`generated/g5-weapon-event.ts` client 接入（G5 无页面，client 供后续 G7/G8 复用）。

### 3.5 历史契约测试的受控后继更新（已获授权，将逐项记录）

- G4 契约测试：运行时路由图断言 96 → 99（受控后继包含；证明 G4 96 条 `api.route.001-096` 的 route_id/permission/audit 与 CB-1.9.0 一致）。

## 4. 后向不变量（激活必须证明）

3. G4 批次导入/训练类型修订/编队上下文闭环在 CB-1.10.0 下行为不变（复用 G4 验收，改读 active 基线）。

5. WebEngine 验证（CB-1.10.0 下 Shell/三主题/Ribbon 与既有 G4 闭环一致）→ 证据。

## 7. 剩余激活工作（吸收首轮复核 10 项必改，作为激活退出门）

以下为激活前必须完成并在复验中证明的工作（§0 已修复项不计）：

1. **受信任能力解析器**（复核高风险#1）：`production.py` 的 G4/G5 能力激活由**经 lock/lineage 校验的 approval 工件**计算，禁止按目录名/裸 JSON 字符串激活；`g4_active` 改为"G4 能力 ∈ active"，并新增 G5 能力判定。后向不变量：CB-1.9.0 下行为与现状一致。
2. **G5 三路由权限与 `EXACT_WE_RELEASE_CONTEXT_SCOPE`**（复核阻断#6）：window=`RAW_DATA_READ+weapon_event.window.read`、perspective=`DERIVED_DATA_READ+weapon_event.perspective.read`、detail=`DERIVED_DATA_READ+weapon_event.read`（已修）；授权中间件需将 WE 的 exact release/context/batch 传入 ResourceContext（当前 `unified.py`/`api.py` 仅传 path）。
3. **DTO 单一来源**（复核设计#3）：`CROSS_LAYER_DTO_CONTRACTS` 为唯一权威，Python/TS 由其生成；门禁逐字段比较名称/类型/必填性/provenance（当前 start/end 与 provenance 已对齐，需补生成与门禁）。
4. **跨批次 ingress 不变量**（复核阻断#4，已修 detector/identity）：canonical Source/Store adapter 必须在边界拒绝跨批次 fact 并审计。
5. **四态运行时语义**（复核高风险#2，已修读模型）：`CAPABILITY_DISABLED`/`ADAPTER_UNAVAILABLE`/`EMPTY`/`READY` 在 API 与前端一致呈现；404 仅表 READY 后端下精确 WE 不存在。
6. **双基线数据根复用验证**（复核设计#6）：同一真实 SQLite/PostgreSQL 数据根在 CB-1.9.0 与 CB-1.10.0 下无迁移复用（只读打开、写后回滚、manifest 不变）。
7. **原子回滚**（复核设计#7）：baseline、generated authority、gateway、frontend bootstrap、route registration、数据根 manifest 作为原子单元切换；部分失败 fail-closed。
8. **Cluster 稳定与查询源**（复核中风险#2/#3，已修）：cluster_id 仅由排序 WE id 集合派生；detail 经关系层查询。
9. **直接 API 负面测试**（复核设计#9）：无权限 403、错误 release scope、错误 batch scope、非法 perspective 422、未知 WE 404、适配器不可用 503。
10. **状态机**：G5 全程 `IN_PROGRESS`；全部阻断项修复且复验通过后才可申请 `CLOSED_LOCAL_WITH_GATES`。

## 8. v4 最终实施与关闭记录（2026-11-07）

1. `tpaa_runtime.gui_capabilities` 使用精确锁哈希、受控工件数量和 approval 状态解析 G2～G5，目录名不能单独激活能力；

9. 直接 API 负测覆盖精确作用域、错误作用域、通配作用域、非法 perspective、未知 WE 及能力未注册；
