## 1. Patch 目的与边界

本 Patch 将“综合对抗批次的武器发射事件导航”和“单次发射的攻防双方复盘”补充为 TPAA 的明确总体业务能力，并明确每个发射事件的数据观察窗口如何确定。

本 Patch 解决的不是重新设计 WVR/BVR/Strike 的专业指标体系，而是补足原总体方案中尚未被明确落实为统一业务入口和双侧复盘流程的部分。

### 1.1 本 Patch 增加

1. 批次级武器发射事件统一入口。
2. 一次实际武器发射作为一个独立 Weapon Event（WE）导航对象。
3. 空战事件的射手视角与目标/防御方视角。
4. WVR/BVR 单机、编队页面的双视角交互语义。
5. Strike 单机、编队页面仅保留射手视角；目标信息、目标效果和正式裁决仍属于攻击过程证据。
6. Training Episode、Weapon Event、Attack Cluster 三者的关系边界。
7. 射手侧与目标侧分别确定的数据观察窗口，以及允许窗口重叠的规则。
8. 武器终止、结果观察结束、正式裁决的独立状态语义。
9. V01 历史多批次训练综合总览及其与 V26 单批次事件复盘的职责边界。
10. Batch 级简单对抗/混合对抗/综合对抗训练类型，与 WVR/BVR/Strike 行为类别的分离。
11. 击杀比、敌我交换比、任务达成率等任务级趋势的展示边界和正式指标门禁。
12. 日期范围、机型、训练类型统一筛选及导入阶段训练类型登记。

### 1.2 本 Patch 不改变

- 四类训练类型：Basic Flight、WVR、BVR、Strike。
- `Session → Episode → Stage` 的既有主干及 Stage Registry 定义权。
- C/W/P/A/J/M 的事实边界。
- P1 116 项指标的公式、semantic identity、输入绑定和趋势资格。
- 既有射手视角专项页面的主体指标、图表和分析内容；本次只增加目标/防御方视角及事件窗口上下文。
- 官方裁决 J 的权威边界。
- 不生成现实武器包线、最佳发射几何、Pk 预测或战术优化建议。

## 2. 核心对象与术语

### 2.1 批次工作集（Batch Workset）

“批次”是用户加载和筛选多架飞机、多架次、多种训练行为的工作范围，是 GUI/应用层的聚合入口，不自动等同于一个新的 Canonical `training_session` 持久化对象。

批次工作集必须引用其包含的精确 Session、Sortie、Context、Release 和数据来源。若一个批次聚合多个 `training_session`，不得在没有批准时间变换和跨 Session 关系的情况下直接拼接时间轴。

### 2.2 Training Episode

继续使用 Canonical 中既有 Training Episode。一次交战过程通常对应一个 WVR/BVR Episode；一个 Episode 可以包含多次武器发射、多个 Stage、多个 Event/Relation。

本 Patch 不创建第二套“Engagement Episode”对象，也不以武器发射事件替代 Training Episode。

### 2.3 Weapon Event（WE）

一次实际武器发射/释放动作对应一个独立 Weapon Event。每一枚独立发射的武器均有自己的事件身份、发射锚点、武器终止状态和结果关联。

Weapon Event 是 Event Graph / TPAA-M Chain 中的事件语义对象，也是批次总览的主要导航对象；它不是一个新的训练科目，也不是新的 Stage。

### 2.4 Attack Cluster

Attack Cluster 用于关联同一次齐射、同一组协同攻击或经规则确认的相关发射。

- 一枚武器：一个 WE。
- 一次多弹齐射：每枚武器各有一个 WE，同时共享 Attack Cluster 关联。
- 一个 Episode：可以包含多个 WE，也可以包含多个 Attack Cluster。
- Attack Cluster 不替代 Episode，也不把多枚武器合并成一个发射事件。

### 2.5 射手视角与目标/防御方视角

同一个 WE 同时具有两套可独立查看的证据投影：

- **射手视角（Shooter Perspective）：** 发射方的目标信息、识别/关联、决策、发射动作、发射后支持/制导、协同分工和结果关联。
- **目标/防御方视角（Target/Defender Perspective）：** 被攻击方当时可获得的信息、告警、威胁判断的可观察代理、实际防御动作、系统状态和结果。

两套视角共用 WE ID、Session Time、Episode/Stage 和正式裁决引用，但不能共用一份“视角数据”冒充双方证据。

### 2.6 单机与编队 Scope

单机和编队是同一 WE 的不同评价 Scope，不是不同的发射事件。

- Individual：选定射手或目标飞机的主体证据。
- Team：选定射手编队或目标编队的成员证据、共享信息、通信、任务/角色关系和团队结果。
- Team 视图必须保留各成员自己的 `P_i` 和 `A_i`，不得只显示一个融合后的“团队态势”，也不得把团队结果复制给成员。

## 3. 批次级统一工作流

### 3.1 主工作流

1. 加载一个批次工作集。
2. 进入批次发射事件总览。
3. 展示批次内所有已识别武器发射事件的时间线、类别、射手、目标、架次、编队、Attack Cluster、Episode 和裁决状态。
4. 按武器类型为主、发射几何为辅，将事件分类为 WVR、BVR、Strike；不能确定的事件进入待确认，不静默猜测。
5. 进入相应行为类别的单机或编队页面。
6. 在类别页面选择同类 WE，进入该次发射的详细复盘。
7. 空战页面可切换射手/目标视角；Strike 页面仅保留射手视角。
8. 通过同一 WE 的事件窗口、Master Timeline 和回放入口联动证据。

### 3.2 页面组织

| 行为类别 | 单机页面 | 编队页面 | 视角 |
|---|---|---|---|
| WVR | V05 | V20 | 射手 + 目标/防御方 |
| BVR | V04 | V08 | 射手 + 目标/防御方 |
| Strike | V06 | V21 | 仅射手 |
| Basic Flight | V07 | V19 | 独立入口，不受发射主线控制 |

现有 V05/V20/V04/V08/V06/V21 的射手侧主体内容保留。目标侧使用独立的内容投影，不得通过替换标题或只切换按钮状态来模拟视角切换。

### 3.3 批次总览统计

批次总览可以统计 WVR、BVR、Strike 的发射事件数、正式裁决状态、已知结果和待确认数量。统计必须遵守：

- “发射事件数”按独立 WE 计数，不按 Attack Cluster 计数。
- Attack Cluster 数量单独统计。
- 已裁决与未裁决分开统计。
- 分类待确认与裁决待确认是两种不同状态。
- 无正式 J 时不得推断官方命中、脱靶或任务成功。

## 4. 行为类别归类规则

### 4.1 主次依据

- 主依据：武器类型/训练武器记录中的规范化武器类别。
- 辅助依据：发射时的训练几何、Episode/Stage、训练想定任务类型。
- 冲突处理：武器类型与几何提示不一致时保留默认类型分类，同时标记“分类例外待确认”；不静默改变类别。
- 未知类型：进入 `UNCLASSIFIED / 待确认`，不强制归入三类。

### 4.2 Demo 当前示例映射

| 武器类型示例 | 默认类别 |
|---|---|
| 红外空空导弹、航炮/机炮、近距空空武器 | WVR |
| 中距/远距空空导弹 | BVR |
| 空地导弹、制导炸弹等对地训练武器 | Strike |

正式系统的映射必须由版本化规则/Context artifact 管理，保存规则版本、原始武器类型、归类结果、几何校验结果、例外原因和人工修订记录。

## 5. 攻防双方的证据与展示边界

### 5.1 空战射手视角

保留既有射手页面主体，按实际可用证据展示：

- 发射前：目标信息可获得性、航迹建立/连续性、识别/关联、任务/角色、决策事件。
- 发射时：训练武器动作、发射时刻、关联目标、武器/平台状态。
- 发射后：支持/制导/通信/协同分工、武器状态、结果关联。
- 结果：仅使用批准的 J；无 J 显示 unavailable / N_A。

### 5.2 空战目标/防御方视角

目标侧展示内容必须以目标成员自身可获得的信息和可观察动作作为依据：

- 发射前/威胁前状态：目标飞机状态、已有任务/态势上下文；
- 威胁信息：目标侧首次可获得的 cue/告警/航迹/数据链信息及来源；
- 防御响应：告警后可观察的动作、机动状态、模式/反制/通信记录；
- 过程关系：cue-to-response、信息传递、成员间差异；
- 结果：武器终止状态、正式裁决、目标状态和任务影响。

**禁止**以 Ground Truth W 替代目标当时可获得的 P_i；没有告警/防御数据时显示“未记录/证据缺失”，不得推断目标必然知道或采取了某动作。

### 5.3 WVR 单机目标视角

重点是目标飞机自身的威胁信息、告警、可观察防御动作、目标状态和裁决关联。几何/状态显示用于复盘，不产生现实战术建议。

### 5.4 BVR 单机目标视角

重点是目标侧的 RWR/ESM/机载告警/经证实的 TDL 信息、威胁信息时序、目标侧可观察响应、信息来源和结果关联。各类信息源必须区分 onboard sensor、TDL、fused 和 inferred。

### 5.5 WVR/BVR 编队目标视角

重点是被攻击成员与其他编队成员之间的：

- 各成员首次获得威胁信息的时间差；
- 成员各自的 P_i 及其一致/未知/冲突状态；
- 目标侧信息共享与通信事件；
- 被攻击成员及其他成员的实际防御动作；
- 编队成员关系、队形/间隔和任务状态；
- 团队过程与正式结果的独立呈现。

### 5.6 Strike 单机/编队

Strike 不提供空战式“目标/防御方视角”切换。V06/V21 保留射手视角；目标信息、目标关联/指定、目标效果和正式靶场/模拟裁决作为射手攻击过程中的证据面板展示。

未来如需评价地面防空单元，应另设防空单元/目标防御评价范围，不将其伪装成空中目标飞机视角。

### 5.7 目标/防御方视角的可视化复盘组织

V05（视距内单机）、V04（超视距单机）、V20（视距内编队）、V08（超视距编队）的目标/防御方视角必须作为独立的复盘投影，而不是将射手页面文字替换为另一组文字，也不得重复展示事件时间窗口页面的多轨甘特图。页面围绕“目标侧态势—威胁信息—响应动作—结果证据”组织。

**单机目标/防御方视角**采用四个主要可视化区域及底部结果条：

1. **目标侧来袭态势图**：以被攻击飞机为中心，展示目标航迹/姿态、来袭方位、关联武器轨迹或相对几何。方位、距离、航向、轨迹必须来自同一有效时间基准下的目标侧/关联轨迹证据；缺少位置或时间对齐时，只显示“几何不可用/示意关系”，不得生成貌似真实的坐标和距离。WVR 强调近距相对态势和目标状态变化；BVR 强调目标侧远距威胁方向、可获得威胁源及其信息更新时间。
2. **目标侧威胁信息形成图**：用来源卡片/状态标识展示首次可获得威胁信息、来源类型、来源实体、时间和证据状态。明确区分 onboard sensor/alert、TDL/shared、fused 和 inferred；推断信息不得伪装成传感器原始记录。
3. **告警—响应—结果关键事件链**：按离散事件节点展示 T1、目标侧首次 cue、首次可观察响应、T2、J 等时刻。节点可点击并驱动 Master Time Cursor、相关证据和回放定位。该图是事件时序，不是观察窗口区间图；缺失节点显示未记录/未知，不用连线补造事实。
4. **目标防御动作与状态变化图**：依据目标侧有效遥测展示航向、速度、高度、姿态/载荷因子、模式/反制等可用状态曲线或动作标记。只展示存在的参数；缺少数据时明确显示缺失。响应前后变化是事实描述，不自动等同于有效规避或成功防御。
5. **底部结果与证据条**：分开展示武器终止状态、正式裁决 J、P_i/A_i/J 证据覆盖、观察窗口状态及数据质量。终止、裁决和观察闭合仍保持三个独立状态。

**编队目标/防御方视角**采用不同于单机的四个可视化区域及底部结果条：

1. **目标编队态势与受威胁成员图**：按有效时间内的编队 Context 展示成员关系，突出被攻击成员；成员位置只有在有有效轨迹时才按真实位置绘制，否则使用明确标注的编队关系示意图。
2. **成员威胁信息与响应矩阵**：逐成员展示 P_i 首次获得时间、来源、可用状态、A_i 首次可观察动作及响应间隔。成员级缺失不得由团队融合态势填补。
3. **成员防御动作时序**：按成员泳道展示威胁信息和动作的离散时间点，并可点击成员或事件点联动其他面板。该图展示成员事件，不表示各成员的完整事件窗口。
4. **信息共享与协同响应关系图**：编队成员关系来自 Context；信息共享/转发边必须由带时间戳和来源的通信/TDL/Relation 证据支持。没有共享证据时只展示成员关系，不推断共享方向、接收者或协同责任。
5. **底部结果与证据条**：同时展示成员 P_i/A_i 覆盖、编队层通信/关系证据、武器终止和正式裁决；不得把单一成员的结果复制为全队结果。

**事件窗口甘特图唯一归属**：T0-S/T0-T/T1/T2/T3 的独立观察区间、重叠关系和数据覆盖边界只在“事件时间窗口”专页/弹窗中展示。目标/防御方页面不得再次嵌入相同多轨窗口甘特图；页面保留“打开独立事件时间窗口”入口即可。目标页的事件链和成员动作时序用于解释过程，不能替代窗口边界。

所有可视化必须有图例、单位、时间基准、来源和数据质量状态。Demo 合成数据须显著标注“示意”，生产页面只能用真实证据投影填充；缺少数据时优先显示 N/A/未提供，不得为了视觉完整而造数。

## 6. 武器发射事件时间窗口

### 6.1 总体原则

批次原始数据保持完整、连续的 Session Time 时间序列。系统不把批次数据强制切成首尾相接、互斥的发射片段。

每个 WE 是对同一份 Canonical/World/Action/Evidence 数据的独立关联视图。多个 WE 可以引用同一原始时间序列记录，原始事实不因多次引用而重复存储。

### 6.2 五个时间锚点

| 时间锚点 | 名称 | 定义 |
|---|---|---|
| T0-S | 射手侧窗口起点 | 与本次发射有关的最早射手侧目标信息/航迹/决策前置证据，或有明确规则依据的上下文起点 |
| T0-T | 目标侧窗口起点 | 目标侧用于重建威胁前状态的最早相关上下文证据；不等同于首次告警时间 |
| T1 | 实际发射锚点 | 规范化训练武器发射/释放动作的 Session Time |
| T2 | 武器终止时刻 | 经权威记录确认的命中、脱靶、拦截、自毁、中止、超时或其他终止时刻；未知时保持未知 |
| T3 | 结果观察结束 | 该事件的结果观察窗口结束或数据覆盖边界；必须标明是已闭合的观察结束还是仅为当前数据覆盖截止 |

此外，首次目标侧 cue/告警、首次防御动作、官方裁决 J 的时间戳应分别保留，不得混为 T0/T2/T3。

### 6.3 两侧独立窗口

- 射手侧窗口：`[T0-S, T3)`。
- 目标侧窗口：`[T0-T, T3)`，若目标侧不适用或没有可用数据则显式标记。
- 武器状态窗口：从 T1 到 T2；若 T2 未知，则仅展示到数据覆盖截止并标注未确认终止。
- 终止后结果观察窗口：从 T2 到 T3；若 T2 或 T3 缺失，不伪造完整窗口。

T0-T 可以早于目标首次 cue/告警，以保留目标在尚未获得威胁信息之前的状态上下文。首次 cue 是单独事件标记。

### 6.4 允许窗口重叠

不同 WE 的窗口允许重叠，包括：

- 同一 Attack Cluster 中多枚武器的窗口；
- 同一 Episode 内连续/交错发射的窗口；
- 同一架飞机的前一枚武器尚未终止、后一枚武器已经发射的情况；
- 同一目标在同一时间段内关联多个来袭事件。

不得使用“上一发事件结束时刻 + 一个采样间隔”作为下一发事件的默认 T0。下一事件的 T0 必须依据它自己的前置证据或版本化上下文窗口确定。

### 6.5 终止、结果与闭合状态分离

必须分别维护：

1. Weapon terminal state：已观测终止 / 终止未知；
2. Adjudication state：已获得批准 J / 待确认 / 不适用；
3. Observation-window state：已闭合 / 部分覆盖 / 仍开放。

武器已终止不等于正式裁决已完成；正式裁决可以晚于 T2；数据覆盖结束也不等于武器事件已终止。

### 6.6 时间与数据质量约束

所有窗口使用权威 Session Time 和半开区间 `[start,end)`。源时钟必须经过批准的 TimeTransform、clock reset/segment 和 Alignment Domain 处理。

- `RESOLVED`：可用于正式窗口/正式产品。
- `EXTRAPOLATED`：仅用于诊断或明确标注的可选增强。
- `UNRESOLVED`：保留原始证据，但不进入正式统一时间窗口。
- `INVALID`：拒绝进入正式窗口。

Clock reset、数据 gap、Series boundary、authority switch 和身份不确定必须保留并可视化，不得排序拼接成连续时间。

## 7. 无发射行为的归属

探测、接敌、规避、告警、通信等没有对应武器发射的行为，仍然是 Episode/Event Graph 中的事实或关系证据：

- 若存在关联来袭 WE，按 `RESPONDS_TO`、`AFFECTS`、`EVIDENCE_FOR` 等关系挂接到目标/防御方视角。
- 若没有对应 WE，在批次全过程时间线中显示，不创建虚假的 Weapon Event，也不作为独立武器发射事件评分对象。
- 不得因为“没有发射事件”而删除这些行为；它们仍可按既有 Stage、训练指标和数据产品规则作为相关证据。

## 8. 红蓝与编队关系

红蓝关系和编队成员关系属于批次/想定 Context 的有效时间投影，不是飞机的永久固有属性。

- 编队设置阵营，成员飞机继承所属编队阵营。
- 独立目标单独设置阵营；作为参演飞机的空中目标继承其所属编队阵营。
- 同一有效时刻一架飞机不得重复属于两个编队。
- 若编队成员关系在批次中途发生变化，必须按有效时间记录，不得用批次结束时的编成反推全程。
- 主视角切换只改变筛选/展示角色，不改变原始事件、射手、目标和正式裁决事实。

5. 过程表现与最终结果分开呈现。
6. 116 项 P1 指标语义和 661 项输入绑定不因本 Patch 改变。
7. 未实现/未验证能力不得在 UI 中表现为已可用的正式评价能力。

## 11. 验收标准（总体设计层）

- 一个批次可汇总多个飞机、架次和多种行为类别，不要求一个架次只对应一种训练类型。
- 每次武器实际发射独立显示一个 WE；齐射多发不合并。
- 同一 Episode 可关联多个 WE；Attack Cluster 独立表达齐射/关联关系。
- 空战 WE 可在射手与目标/防御方两种视角间切换，两个视角主体内容不同且共用事件 ID。
- 四个空战目标侧页面均以态势图、威胁信息、离散事件链、动作/成员可视化和结果证据组织；单机与编队页面具有不同分析结构。
- 目标侧页面不重复展示事件窗口多轨甘特图；窗口区间/重叠只在独立事件时间窗口中展示。
- 点击目标侧关键事件/成员可联动 Master Time Cursor、相关图表和回放上下文；缺少来源证据时不生成伪几何、伪共享关系或伪遥测。
- Strike 只显示射手视角；目标信息和结果证据仍可见。
- 事件窗口显示两侧起点、发射锚点、终止状态、结果观察结束和窗口状态。
- 不同事件窗口可重叠，系统不按前一事件结束时间强制切片。
- 缺失的目标侧 P_i、A_i、J、T2 或 T3 明确显示缺失/未知/待确认，不填造数据。
- 原始批次时间序列保持连续，事件窗口只建立引用/投影，不重复存储原始事实。

## 13. 历史多批次训练综合总览（V01）

### 13.1 产品定位与边界

V01“训练总览”定位为**跨多个历史训练批次的综合统计与趋势分析入口**，不再承担单个批次全过程复盘职责。

- V01 面向多个历史批次，回答“历史训练活动如何变化、不同训练类型的批次分布如何、任务级结果和装备性能如何变化”。
- V26 面向一个已加载批次，回答“该批次内发生了哪些武器发射事件、每次发射如何复盘”。
- V04～V08、V20、V21 等专项页面继续面向选定发射事件，不因 V01 调整而改变主体分析内容。
- V07/V19 基本飞行仍保留独立复盘入口；基本飞行数据不要求生成 Weapon Event。
- V09 继续承担深入的跨批次训练成长分析；V10～V16 继续承担装备性能专项分析。V01 只提供概览和进入专项页面的导航。

V01 不得将多个批次的原始时间序列直接拼接成一个连续 Session 时间轴。跨批次统计是基于各批次权威汇总产品的聚合，不改变各 Session 自身的时间基准和数据边界。

### 13.2 批次训练类型、训练行为类别与训练科目域的区分

V01 引入的批次级“训练类型”是批次元数据，显示值为：

- 简单对抗；
- 混合对抗；
- 综合对抗。

该字段用于描述批次的组织/训练类型，不替代既有训练科目域，也不替代 Weapon Event 行为类别。三者必须严格区分：

| 分类维度 | 典型值 | 作用范围 | 用途 |
|---|---|---|---|
| 批次训练类型 | 简单对抗、混合对抗、综合对抗 | Batch | 历史批次筛选、批次分组和统计分层 |
| 武器发射行为类别 | WVR、BVR、Strike | 单个 Weapon Event | 对发射事件归类并路由至专项复盘页面 |
| 训练科目/评价域 | 基本飞行、WVR、BVR、Strike | Episode / Stage / 评价产品 | 组织训练评价方法、Stage 和指标 |

一个混合或综合对抗批次可以同时包含 WVR、BVR、Strike 多类 Weapon Event，也可以包含没有武器发射的接敌、探测、规避、基本飞行和其他事件。不得仅凭某一类 Weapon Event 的数量自动推断批次训练类型。

批次训练类型由用户在导入/登记工作台显式选择，并作为批次元数据保存。其值应有受控枚举、来源、设置时间和修改审计；生产系统不得只保存在浏览器运行时状态中。

### 13.3 V01 页面信息架构

V01 的统计范围控件统一包括：

1. 起始日期；
2. 结束日期；
3. 机型；
4. 训练类型。

同一筛选上下文必须一致作用于 KPI、趋势图、历史批次列表和选中批次摘要。日期范围无效时显示明确提示和空结果，不产生 NaN 或误导性统计。

V01 页面主体按三行组织：

| 行 | 面板 | 主要职责 |
|---|---|---|
| 第一行 | 任务级指标趋势；历史训练活动趋势 | 对比任务级结果指标，以及各批次 Weapon Event / Episode 活动数量 |
| 第二行 | 训练结果与裁决状态趋势；训练行为类别构成；装备性能历史趋势 | 分析正式裁决状态、WVR/BVR/Strike 发射构成和装备指标变化 |
| 第三行 | 历史训练批次；选中批次摘要 | 浏览符合筛选条件的批次，查看所选批次汇总、数据准备状态和可用操作 |

顶部 KPI 至少区分历史批次数、飞行架次、交战过程（Episode）、武器发射事件（WE）、已正式裁决事件和数据资格摘要。计数必须按稳定对象身份去重；WE 数按独立 WE 计数，不按 Attack Cluster 计数。

历史批次列表显示批次日期、批次编号、训练类型标签、架次数量、发射事件数量和数据状态。选中批次摘要不得把其他批次的事件明细冒充为当前批次数据。只有精确关联且已加载逐事件明细的批次，才允许显示进入 V26 的详细复盘入口；仅有汇总记录的批次应显示“仅有汇总/明细未加载”等状态。

### 13.4 任务级指标趋势

V01 增加以下任务级趋势指标：

1. **击杀比**；
2. **敌我交换比**；
3. **任务达成率**。

V30/V31/V32 Demo 暂用以下演示口径：

- 击杀比 = 经批准确认的敌方击杀数 / 有效空战交战数；
- 敌我交换比 = 经批准确认的敌方损失数 / 被评估方确认损失数；
- 任务达成率 = 已达成任务目标数 / 计划任务目标数。

上述公式只是 Demo 的暂定展示口径，**不是已批准的 P1 指标定义，也不自动获得正式指标身份**。正式生产定义必须经指标字典/方法权威批准，至少明确统计 Scope、对象去重、有效交战定义、击杀/损失归属、裁决来源、目标计划基数、时间窗口和被评估方视角。

计算和展示规则：

- 击杀、损失和结果必须引用批准的官方裁决 J 或经批准的权威任务结果；不得仅凭 Weapon Event 的“命中/未命中”演示标签推断正式击杀。
- 敌我交换比的分子、分母必须明确对应当前被评估方视角；切换评估方时应按权威归属重新计算，不得仅交换标签。
- 分母为零时显示 N/A/不可计算及 reason code，不得显示无穷大、用零代替或静默剔除。
- 关键输入缺失、裁决未完成或数据覆盖不足时，指标状态应为 pending/unavailable，并显示覆盖与资格信息。
- 跨批次汇总比值时，若统计语义可比，应先汇总各批次的分子和分母再计算比值；不得对批次比值进行无权重简单平均。
- 任务达成率必须基于想定/任务目标清单及正式达成状态，不得把武器命中数直接当作已达成任务目标数。
- 指标公式、输入绑定、semantic identity 和成熟度仍由既有指标治理机制管理；本 Patch 不修改 P1 116 项指标。

### 13.5 历史活动、裁决、类别与装备趋势

- **历史训练活动趋势：** 按批次日期展示独立 WE 数量和 Episode 数量；跨 Session 只做批次聚合，不拼接原始时间序列。
- **训练结果与裁决状态趋势：** 分开展示正式裁决结果与待裁决状态；未裁决事件不得计入已裁决命中/损失。
- **训练行为类别构成：** 按 WE 的行为类别统计 WVR、BVR、Strike；该筛选维度不得与批次训练类型混为一谈。
- **装备性能历史趋势：** 仅比较相同指标定义/版本、单位、机型/构型和可比条件下的指标序列。持续盘旋角速度、探测距离 R50、告警响应时间等摘要趋势必须显示指标口径、样本数、数据覆盖和资格状态；不可比样本不得强行连线。
- 所有筛选控件必须作用于同一批次集合；某一面板没有合格数据时显示无数据/不适用，不以合成数据填补生产缺失。

### 13.6 导入工作台的训练类型登记

导入工作台应在批次登记阶段提供“训练类型”选择，选项为简单对抗、混合对抗、综合对抗。

- 训练类型随批次元数据持久化，并进入导入队列、批次摘要和历史批次列表。
- 用户提交导入时必须确认训练类型；默认展示值不能替代明确确认。
- 批次登记成功但解析尚未完成时，状态应为“已登记/待解析”，不得计入已完成数据资格或生成正式任务指标。
- 后续修改训练类型应记录操作者、时间、旧值、新值和原因；不得静默覆盖历史分类。
- 未知/未选择类型应保持未分类状态并提示，不得猜测为综合对抗。

### 13.7 V33 KPI 卡片溢出修复与布局空间重分配

V32 虽然把外层网格 `gap` 调整为 10px，但 KPI 卡片自身由三个内容轨道（14px + 25px + 12px）、上下内边距（12px）和边框（2px）组成，实际需要约 65px；V32 却只给 KPI 行分配 55px。子卡片向下溢出约 10px，侵占了网格原本保留的间距。因此仅增加 `gap` 并不能解决可见边框贴合问题。

V33 同时修正父行与子卡片的真实尺寸：

- KPI 网格行分配 `68px`；
- 每张 KPI 卡片显式使用 `box-sizing:border-box`、`height/min-height=65px`，并在 68px 网格行内垂直居中；
- 外层网格行列间距维持 `10px`；
- 第一、第二行趋势面板各 `168px`；
- 第三行使用 `minmax(180px, 1fr)`，在 1600×900 参考画布下实际为 `192px`；
- V33 第三行历史批次和选中批次摘要较 V32 的 205px 再缩减约 13px；较 V31 的 246px 共缩减约 54px；
- 在 1600×900 参考画布下，KPI 卡片实际边框底部至第一行趋势面板顶部约有 11.5px 可见间隔；在 1280×720 缩放画布下约有 8px 可见间隔；
- 历史批次表格在缩小后的面板内滚动；选中批次摘要内容必须在面板内完整容纳，不得裁切；
- 各行之间必须保留可见间距，不能依靠边框贴合来表示相邻；
- 验收必须测量 KPI 卡片本身及其父网格行的 bounding box，不能只检查父容器间距或 DOM 顺序。

在 1600×900 参考画布下，V01 内容区域仍为 `top=166px`、`height=694px`，网格行为 `36px / 68px / 168px / 168px / minmax(180px, 1fr) / 12px`。该尺寸是当前 Demo 的参考布局约束，不是生产 UI 的唯一像素规范；生产 GUI 应落实相同的信息层级、真实盒模型约束和不重叠要求。

### 13.8 数据真实性声明

当前 V29～V33 的多批次历史记录、任务级指标曲线、装备性能曲线和部分裁决统计含合成演示数据。只有 Demo 明确标记为已加载逐事件明细的批次，才可进入其真实 Demo 明细页面；其余历史批次只能用于展示汇总筛选和趋势交互。

生产 V01 必须由权威 Batch、Session、Sortie、Episode、Weapon Event、Adjudication、Aircraft/Model、Metric、Evidence 和 Data Quality 产品生成。Demo 通过不代表真实批次聚合、指标算法或后端持久化已经实现。

### 13.9 V01 总体验收标准

- 可在同一日期范围内浏览多个历史批次，而非只显示当前批次。
- 日期、机型、批次训练类型筛选对 KPI、趋势图和批次列表保持一致。
- 批次训练类型与 WVR/BVR/Strike 行为类别在数据模型和界面上明确分离。
- 导入工作台所选训练类型能够写入批次登记，并在 V01 列表和摘要中显示。
- 任务级指标显示击杀比、敌我交换比和任务达成率，且标注演示/正式状态和口径。
- 正式裁决缺失、分母为零、数据覆盖不足时显示 N/A/pending，不推断结果。
- 第一行包含两个趋势面板，第二行包含三个分析面板，第三行包含历史批次和选中批次摘要。
- 六张 KPI 卡片均不超出其 68px 网格行，卡片真实边框与第一行趋势面板保持可见间隔；各趋势行及第三行与页脚之间均无重叠。
- 仅有汇总的批次不得跳转到其他批次的逐事件复盘。
- 三种主题及目标分辨率下页面无文字遮挡、图表覆盖或横向溢出。
